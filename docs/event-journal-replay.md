# Event Journal and Replay

This document explains how event journaling (recording) and replay work in the current platform, how they are used for production debugging, and how the Aeron Archive changes the replay workflow.

---

## Current Journaling Architecture

### How Events Are Recorded

Two independent recording mechanisms run during live operation:

#### 1. BinaryMessageStore (Corefile Journal)

`com.core.platform.applications.utilities.BinaryMessageStore` is a `BusClient` application that writes every received event to a sequential binary file — the **corefile**.

```
Event Stream ──► BusClient Dispatcher ──► BinaryMessageStore
                 (addListenerBeforeDispatch)       │
                                                   ▼
                                        {session}.events.dat
                                        ┌──────────────────────┐
                                        │ [2-byte len][message]│
                                        │ [2-byte len][message]│
                                        │ [2-byte len][message]│
                                        │ ...                  │
                                        └──────────────────────┘
```

- Writes a **2-byte length prefix** followed by the raw message bytes for each event.
- File is named after the session (e.g., `20260216AA.events.dat`).
- Created on session open, closed on session close.
- **No index file** — sequential access only.
- This is the file used for offline replay and backtesting.

#### 2. ChannelMessageStore (Retransmission Store)

`com.core.platform.bus.mold.ChannelMessageStore` is used by the `MoldBusServer` for live gap recovery (rewinds). It writes **two files**:

```
{session}.events.dat   — raw event data (same content as corefile)
{session}.index.dat    — 8-byte offset per message for O(1) lookup by sequence number
```

- `FileChannelMessageStore` backs both with NIO `FileChannel`s.
- `BufferChannelMessageStore` uses in-memory buffers (test/demo only).
- The `MoldRewinder` reads from this store to serve replay requests.

### Key Difference

| Aspect | BinaryMessageStore (Corefile) | ChannelMessageStore (Retransmit) |
|--------|-------------------------------|-----------------------------------|
| Purpose | Offline replay, debugging, backtesting | Live gap recovery (rewinder) |
| Index | None — sequential only | O(1) by sequence number |
| Written by | BusClient (any node) | BusServer (sequencer node) |
| Files | `{session}.events.dat` | `{session}.events.dat` + `{session}.index.dat` |

## Replaying for Production Bug Investigation

### Scenario

A production bug occurred at ~14:30 on 2026-02-16. The sequencer was running with session `20260216AA`. A corefile `20260216AA.events.dat` was captured by `BinaryMessageStore` on any node.

### Step 1: Obtain the Corefile

Copy the corefile from the production node:

```bash
scp prod-node:/data/logs/20260216AA.events.dat ./
```

### Step 2: Launch in Playback Mode

```bash
./gradlew uberjar
java --add-opens java.base/jdk.internal.misc=ALL-UNNAMED \
  -DSHELL_PATH=platform/src/main/resources:clob/src/main/resources \
  -Dcorefile=20260216AA.events.dat \
  -jar clob/build/libs/core-1.0-SNAPSHOT.jar com.core.platform.Main \
  -s clob.cmd
```

### What Happens Internally

```
Main.java detects -Dcorefile=20260216AA.events.dat
  │
  ├── time = new ManualTime()           ← virtual time, not wall clock
  ├── EventLoop uses runOnce()          ← no blocking select, no updateTime()
  ├── EventLoop.eventsOnly = true       ← skip selector entirely
  │
  ├── Shell loads clob.cmd              ← creates all applications normally
  │
  └── Looks up /playback consumer
      └── FilePlayback.accept("20260216AA.events.dat")
          │
          Loop for each message in corefile:
          │
          ├── Read 2-byte length prefix
          ├── Read message bytes
          ├── Extract timestamp from header
          ├── ManualTime.setNanos(timestamp)    ← time jumps to recorded moment
          ├── Apply MessageTranslator chain     ← schema migration if needed
          ├── Dispatch through FileBusServer
          │     ├── All event listeners fire
          │     ├── Applications process event
          │     ├── Any commands generated by apps are routed back
          │     │   through FileBusServer and dispatched immediately
          │     └── Scheduler.fire() triggers any due tasks at virtual time
          └── Next message
```

### Step 3: Investigate the Bug

During playback, all application logic runs exactly as it did in production:

- **Breakpoints**: attach a debugger, set breakpoints in application handlers.
- **Logging**: enable debug logging (`/vm/log/debugForAll true` in command file) to see detailed state transitions.
- **Modified logic**: change application code, rebuild, replay — see if the fix resolves the issue.
- **Selective replay**: use `FilePlayback.deny(appName)` to suppress specific applications' messages and isolate the bug.
- **Time inspection**: `ManualTime` shows exact virtual time — correlate with production logs.

### Step 4: Reproduce With Modified Code

```bash
# After fixing the bug, replay again to verify:
./gradlew uberjar
java -Dcorefile=20260216AA.events.dat \
  -jar clob/build/libs/core-1.0-SNAPSHOT.jar com.core.platform.Main \
  -s clob-fixed.cmd
```

The fix is validated deterministically — same input events, same time progression, different code path.

### Limitations of Current Replay

| Limitation | Impact |
|------------|--------|
| **Single process only** | Cannot replay across multiple nodes simultaneously |
| **Sequential file format** | Cannot seek to a specific sequence number or time — must replay from the beginning |
| **No compression** | Large corefiles for high-throughput sessions (ReadOnlyFilePlayback supports .gz) |
| **Schema migration required** | If schema has changed since recording, MessageTranslator chain must be maintained |
| **No snapshot support** | Must replay from beginning — cannot skip to a checkpoint |

## Replay With Aeron Archive (Phase 2+)

When Aeron Archive is integrated, the replay model changes significantly. The Archive replaces both `BinaryMessageStore` and `ChannelMessageStore` as the durable journal.

### How Events Are Recorded With Archive

```
Sequencer ExclusivePublication ──► Archive RecordingSession (SourceLocation.LOCAL)
                                        │
                                        ▼
                              /archive/{recordingId}-{position}.rec  (segment files)
                              /archive/catalog                       (recording index)
```

- Archive records **raw Aeron frames** (not the 2-byte-length corefile format).
- Recording is per-stream (channel + streamId), indexed by recording position.
- Catalog provides metadata: start/stop positions, session info, original channel.
- **O(1) seek** to any position in the recording.

### Production Bug Investigation With Archive

#### Step 1: Identify the Recording

Query the Archive catalog to find the recording for the session:

```bash
# Via shell on the Archive node:
/archiveManager/status
# Shows: recordingId=42, channel=aeron:udp?endpoint=224.0.1.1:40456, startPosition=0, stopPosition=...
```

Or programmatically:

```java
archive.listRecordingsForUri(0, 100, eventChannel, eventStreamId,
    (controlSessionId, correlationId, recordingId, ...) -> {
        // Find recording covering the bug timeframe
    });
```

#### Step 2a: Replay Entire Stream (Simple)

Request Archive replay from position 0 to a new unicast endpoint:

```java
long replaySessionId = archive.startReplay(
    recordingId,
    0L,                          // from beginning
    Long.MAX_VALUE,              // to end of recording
    "aeron:udp?endpoint=localhost:20001",
    replayStreamId);
```

The replayed events arrive as a normal Aeron subscription — same format as live. Attach application logic, debugger, or custom analysis tools.

#### Step 2b: Replay From a Specific Position (Targeted)

If the bug occurred around event sequence 500,000, skip ahead:

```java
// Convert sequence number to Archive position
// (requires mapping — see snapshot checkpointSeqNum or index)
long position = archivePositionForSeqNum(500000);

long replaySessionId = archive.startReplay(
    recordingId,
    position,                    // skip to the relevant section
    Long.MAX_VALUE,
    replayChannel, replayStreamId);
```

#### Step 2c: Replay From Latest Snapshot (Fastest)

If snapshots exist (Phase 3), replay from the snapshot closest to the bug:

```
1. Query SnapshotIndex for latest snapshot before the bug timestamp
2. Load snapshot chunks → restore node state
3. Replay deltas from checkpointSeqNum to bug timeframe
4. Investigate with full state context
```

#### Step 3: Multi-Node Replay (Distributed Debugging)

With Archive + `SequencerDrivenTime`, replay across multiple nodes simultaneously:

```
Archive ──► ReplayMerge ──► Multicast (or MDC)
                                │
                  ┌─────────────┼─────────────┐
                  ▼             ▼             ▼
            Node A          Node B          Node N
            (Sequencer)     (OrderBook)     (Pricing)
            ManualTime      Seq.Driven      Seq.Driven
                            Time            Time
```

All nodes replay the same event stream, synchronized by event timestamps. Each node's application logic runs deterministically in virtual time.

#### Step 4: Export Corefile From Archive (Compatibility)

If the existing `FilePlayback` tool is preferred, export an Archive recording to corefile format:

```java
// ArchiveToCorefile utility (new in Phase 2)
// Reads Archive recording, writes 2-byte-length corefile format
ArchiveToCorefile.export(archive, recordingId, startPosition, stopPosition, outputPath);
```

This bridges the old and new replay workflows.

### Comparison: Current vs Archive Replay

| Aspect | Current (Corefile) | Archive (Phase 2+) |
|--------|-------------------|---------------------|
| **Recording format** | 2-byte length + message bytes | Raw Aeron frames in segment files |
| **Index** | None (sequential) or separate index file | Built-in catalog + position-based O(1) seek |
| **Seek to position** | ❌ Must replay from start | ✅ Direct seek to any position |
| **Seek to time** | ❌ Must replay from start | ✅ Via snapshot checkpointSeqNum or binary search |
| **Multi-node replay** | ❌ Single process only | ✅ Replay via multicast/MDC to all nodes |
| **Live merge** | ❌ Offline only | ✅ ReplayMerge transitions to live stream |
| **Compression** | .gz supported (ReadOnlyFilePlayback) | Archive segment files (no built-in compression) |
| **Schema migration** | MessageTranslator chain | Same — events are raw bytes, schema version in header |
| **Gap recovery** | Rewinder reads from ChannelMessageStore | Archive serves replay requests |
| **HA replication** | Manual file copy | Archive replication protocol (self-healing) |
| **Snapshot integration** | ❌ None | ✅ Replay from snapshot + deltas |

## Replay Workflow Summary

### Current Workflow (Production Bug)

```
1. Copy corefile from production node
2. Launch with -Dcorefile=<path>
3. FilePlayback reads file, sets ManualTime, dispatches messages
4. Debug with breakpoints, logging, modified code
5. Replay is deterministic — same input → same behavior
```

### Archive Workflow (Phase 2+)

```
1. Query Archive catalog for recording ID
2. Choose replay strategy:
   a. Full replay: startReplay(recordingId, 0, MAX_VALUE, ...)
   b. Targeted: startReplay(recordingId, positionNearBug, ...)
   c. Snapshot: load snapshot, replay deltas from checkpoint
3. Receive replay on Aeron subscription (same format as live)
4. Optionally replay to multiple nodes via multicast
5. All nodes synchronized via SequencerDrivenTime
6. Debug with full distributed context
```

### Archive Workflow (Node Recovery — Not Bug Investigation)

```
1. Node starts / restarts
2. SnapshotRecovery loads latest valid snapshot from Archive
3. ArchiveReplayClient replays deltas from checkpointSeqNum
4. ReplayMerge transitions to live multicast
5. Node is ready — activator becomes active
```
